Diagnose member and base access in constructor and destructor function-try-block handlers

Abstract

Before (N5054)After P4462R0
 
struct B {};

struct X : B
{
    int m{};
    inline static int s{};

    void f();

    explicit X(int X::* pm) try
    {
        throw 0;
    }
    catch (...)
    {
        (void)m;                 // UB
        (void)this->m;           // UB
        (void)&m;                // UB
        f();                     // UB
        (void)(this->*pm);       // UB
        B* bp = this;            // UB
        B& br = *this;           // UB
        [this] { return m; }();  // UB

        (void)sizeof(m);         // OK
        (void)&X::m;             // OK
        (void)s;                 // OK
        (void)static_cast<void*>(this); // OK

        X* p = this;             // OK
        (void)p->m;              // well-formed; UB
    }
};
 
struct B {};

struct X : B

Direct member and base access in these handlers is undefined behavior. Making it ill-formed is a low-hanging fruit. It catches careless mistakes and replaces UB with compiler diagnostics, which are excellent teachers for beginners.

Existing Practice

Clang issues a diagnostic, while GCC and MSVC do not.

Proposed Wording

Relative to N5054.

Insert a new paragraph after [except.handle]/11:

A potentially-evaluated expression in such a handler (including in the bodies of nested lambda-expressions) that directly refers to a non-static member or base class subobject of the object, using this explicitly or implicitly, is ill-formed.

Alternatively, we can mirror the wording from [expr.prim.id.general]/2, but I think the proposed wording is clear.

Bu işleyicilerde üyelere ve taban sınıflara doğrudan erişim tanımsız davranıştır (UB). Bu tür erişimleri rahatlıkla geçersiz (ill-formed) yapabilir ve dikkatsizlik sonucu oluşabilecek hataları engelleyebiliriz. Ek bir avantaj olarak, bu değişiklikle gelecek derleyici tanıları, yeni yazılımcıların dili öğrenmelerini kolaylaştıracaktır.

Mevcut Durum

Clang halihazırda tanı verirken GCC ve MSVC tanı vermemektedir.

Önerilen Düzenleme

N5054 baz alınarak,

[except.handle]/11’den sonra yeni bir paragraf ekleyin:

A potentially-evaluated expression in such a handler (including in the bodies of nested lambda-expressions) that directly refers to a non-static member or base class subobject of the object, using this explicitly or implicitly, is ill-formed.
Böyle bir işleyicide (iç içe lambda-expression gövdeleri dâhil) yer alan ve this ifadesini açıkça veya örtük olarak kullanarak nesnenin statik olmayan bir üyesine veya taban sınıf alt nesnesine doğrudan atıfta bulunan potentially evaluated bir ifade geçersizdir (ill-formed).

Alternatif olarak, [expr.prim.id.general]/2’deki ifadeyi örnek alabiliriz, ancak önerilen metnin açık olduğunu düşünüyorum.
